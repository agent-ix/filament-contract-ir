# TC-484: Probabilistic nodes on source-declared operations

## Description

Verify the probabilistic join of operation references whose `declaring` node is a source-declared object type: the strict read's kind, timed-root and reward-function checks and the identity-row join's operation, parameter, workload and reward-parameter checks (FR-369-AC-25, FR-369-AC-26; FSpec FR-640-AC-6, FR-640-AC-7). Steps 1 (admission and typed read), 2 and 4 verify the strict-read halves FR-369-AC-27 and FR-369-AC-28; steps 3, 5 and 6 and the golden pair are the identity-row join (`SelectedSourceObjects::join_probabilistic`, QSL-2645).

The golden pair is a checked-in fixture directory (`tests/fixtures/qsl-2645-golden`) holding FR-369-AC-25's package and the expected typed read of its declarations. The test reads the package, compares the typed read with the golden one, and compares the reward function's id with the declared-node id `{package, ["Other", "poke", "reward", "cost"], 0}` the test builds itself, so a reader that resolves the reward through another node, keys it by an ordinal, or drops it from the typed read fails.

## Test Procedure

1. Read FR-369-AC-25's golden package, admit its source-object identity rows and run the join; take the typed read and compare it with the golden typed read; build the reward function's declared-node id and compare it with the function the reward names.
2. Edit a `declaring` to a source `relation`/`population` node; read a variant whose source model has no `dense` time member.
3. Over the admitted package, edit the `operation` to `nudge`, the `parameter` to `j`, a support value to `4`, and drop `O::step` from the workload; join each. Over a package whose entry `p` is typed by a source enumeration with the cases `ACTIVE` and `DONE`, join a support literal naming `DONE` (admitted), a case the enumeration lacks, a case of another enumeration and a literal typed at another enumeration (each refused `InvalidValue` at the literal), and the same literal with the enumeration absent from the enumeration rows (refused at the literal's `type` member).
4. Over the admitted package, rewrite the reward function's `declaration` to `["Other", "poke", "reward", "load"]`, `["Other", "step", "reward", "cost"]` and `["O", "poke", "reward", "cost"]`, each time rewriting the function's `node_id` path and the reward's `expression` target to match; rewrite its `clause` to `"precondition"`; add a second `lock.sources` row and give the function that source's `SourceOwner`, its `declaration` source-map region naming the second source; read each strictly.
5. Over the admitted package, give the reward function the parameter `j` (read by the body) in place of `k`, and no parameter with the constant body `1`; rewrite the reward's `operation` to `nudge`; join each. Read the variant with `Other::poke` declared `poke(x: Clock, k: Int[1, 3])` (identity-row entry `parameters` `x` clock, `k` data; `clock_parameters` `["x"]`) with the reward function listing `x` then `k`, and with it listing `k` alone; join each.
6. Count the join's charges for step 1's package independently of the reader: one work unit per node met, per operation reference joined, per operation entry read, per parameter entry of the operation read, per supertype edge read, per support value checked and per reward function parameter compared, one more for each byte of caller text compared, for an enumeration-typed entry one per enumeration row met and, with the bytes of its text, one per case compared (the second case of an enumeration costs one visit and the bytes of its text more than the first), and for a workload one per lookup element met; count the logical storage units independently: the failure pointer paid first (one container and 256 bytes), one unit for each of the workload's three lists and each element, and for each exact number parsed one unit and one for each nine-digit limb, and for a rational written as a numerator over a denominator the divisor storage one more unit and limb (a hundred-digit support value costs 1 + 12). Join with a budget one work unit short and one logical storage unit short of those counts, a budget that cannot pay for the failure pointer, and read the budget's last success delta and its zero read storage after a join that succeeds.

## Expected Results

- Step 1: admitted by both stages; each declaration keyed by its node; the typed read equals the golden one, the reward `cost` with value type `Int[1, 3]` and the function whose id equals the built declared-node id.
- Step 2: `invalid_package`/`invalid-value` at `declaring`, at the strict read.
- Step 3: `invalid_package`/`invalid-value` at the edited member, at the identity-row join; for the `operation` and the `parameter` the `value` of the literal, the member the strict read names for the same edit over a selected model's node (the test derives it from that refusal).
- Step 3, enumeration entry `p` typed by a source enumeration with the cases `ACTIVE` and `DONE`: a literal typed at the enumeration naming `DONE` is admitted; a case the enumeration lacks, a case of another enumeration and a literal typed at another enumeration each refuse `invalid_package`/`invalid-value` at the literal (`.../members/0/members/0/value`); the enumeration absent from the enumeration rows refuses `invalid_package`/`invalid-value` at the literal's `/type`. The work charged is one visit for each enumeration row met and, with the bytes of its text, one for each case compared: a literal naming the second case costs one visit and the bytes of its text more than one naming the first, rows behind the enumeration's row cost nothing, and every work allowance short of the total stops the join as `Incomplete`.
- Step 4: the owner join admits each package (the second source is lock-selected and its region names it); the probabilistic strict read refuses each `invalid_package`/`invalid-value` at the reward's `/body/members/4/value/target`.
- Step 5: the two parameter edits each `invalid_package`/`invalid-value` at the reward's `/body/members/4/value/target`, and the `nudge` edit at the reward's `operation`, at the identity-row join. The `Clock` variant listing `x` then `k` is admitted; listing `k` alone refuses at the reward's `/body/members/4/value/target` at the identity-row join.
- Step 6: with the full count the join returns `Ok(())` and the last success delta equals the counts; one unit short it stops the join with `Incomplete` at the first uncharged member and records no success delta, so a join that skips the reward's parameter charges, its lookups or its storage charges returns `Ok(())` and fails the test; a budget that cannot pay for the failure pointer stops the join as `Incomplete` with no locus.
